# ربط البلاغات والمستودع — مراجعة ملفات V331، والربط المباشر قيد الإعداد

نوصي بأن تكون هذه المنصة لوحة الإدارة والمتابعة الموحدة، مع بقاء مسؤولية البيانات واضحة.

| المعلومة | المصدر المقترح | الاستخدام في منصتنا |
|---|---|---|
| رقم البلاغ وبياناته الأساسية | منصة البلاغات | استيراد وتحديث بالرقم الخارجي، دون حذف إجراءات الفنيين |
| حالة التنفيذ والصور والملاحظات | النظام الذي ينفذ الفني العمل من خلاله، يحدد قبل الربط | تبادل الحقول المتفق عليها مع تاريخ وتعارضات واضحة |
| رصيد المخزون وحركاته وتكلفة الصرف | منصة المستودع | عرض الرصيد وطلب القطع وربط الصرف والإرجاع بأمر العمل |
| مؤشرات التشغيل والتكاليف والمستخلصات | منصتنا | تجميع من السجلات المعتمدة، ومنع تكرار تكلفة القطع بين الأنظمة |

الربط المفضل API مع Webhooks متى توفرت، ومصالحة دورية لاسترجاع الأحداث الفائتة. البديل المرحلي استيراد ملفات موحدة. لا نكتب مباشرة في قاعدة المنصة الأخرى.

متطلبات التصميم: معرف النظام مع معرف السجل الخارجي، رقم حدث لمنع التكرار، آخر وقت مزامنة، معالجة التحديثات القديمة، سجل محاولات وإعادة محاولة مضبوطة، ومراجعة التعارضات. تحفظ مفاتيح التكامل على الخادم ولا توضع في HTML. صفحة التكامل تعرض آخر نجاح وأخطاء كل مصدر، مع صلاحيات قراءة أو كتابة محددة. عند صرف قطعة أو إرجاعها يحفظ رقم الحركة الأصلي لمنع تكرار الرصيد أو التكلفة.

يبدأ التنفيذ باستيراد للقراءة على بيئة اختبار، ثم اختبار التحديث المتكرر وانقطاع الاتصال وتغير الحالة وإلغاء حركة الصرف. يفعّل تبادل الكتابة بعد تحديد مالك كل حقل ومطابقة عينات وأرقام إجمالية.

المطلوب لتحديد التنفيذ: اسم ورابط كل منصة، وثائق API/Webhooks أو عينة ملفات، والبيانات المطلوب إرسالها في الاتجاهين. لا ترسل كلمات مرور أو مفاتيح سرية في المحادثة.

مراجع تقنية أولية: [Supabase Database Webhooks](https://supabase.com/docs/guides/database/webhooks)، [GitHub webhook best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks). اختيار التفاصيل يعتمد على قدرات المنصتين الفعليتين.
